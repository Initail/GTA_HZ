# 杭州岸线接口与源跨水道路审计

2026-11-11。本轮只读共享输入，只在本目录写研究记录，没有 Blender、浏览器、总资产构建或源码修改。基于 `render-input-v5` / `water-data-v3`、`street-data-v2` 和固定 2026-10-11 PBF。结论是可以沿用反射、植被避让和灯光管线，但 **不能只填空清单或替换深圳地名**。

机读建议见 [contract.json](contract.json)，它是待主集成实施的接口契约，**不是可以直接安装的 infrastructure.json**。数据及源码 SHA256 见 [input-bindings.json](input-bindings.json)。

## 必须处理的最小接口差异

|运行时入口|真实行为|杭州最小接法|
|---|---|---|
|`loadCoastalInfrastructure`|要求 schema 1；crossings≤2000、parkLights≤400。杭州已不调用径向桥高采样|真实跨水桥有 2049 条源道路、2132 个 >0.1 game 湿区片段，需调整有界上限（如4096）并验证来源；不能截断到2000|
|`createBayWater`|shore URL 直接交给 Texture；红通道固定乘120，`maxDistance` 不参与计算|城市专属实际PNG、正确URL与范围，最大距离保持120；继续 `flattenWater=false` 和 `extendHorizon=false`|
|道路植被|crossings 用于避让，半径取 `max(width/2+5,ramp)`|杭州清单兼容字段 ramp=0，保留实际桥廊宽度；现有 source-node 高度负责道路，不再用70 game半径清空岸上树木|
|公园灯杆与局部灯|杆模板约11.7，局部发光点11.56；没有读取 ParkLight.height|沿用约12高的通用模板可保持接口；更低/不同杭州灯具需同步模型和发光位置；不能仅改JSON的height|
|水岸材质|只认 `terrain_pavement`、`terrain_concrete`、`coastal_shore_*`；湿痕仍按世界 y≈0|必须匹配杭州实际分块网格或语义metadata，城市阳台湿线改用本地暂定水面参考；不能只移动中心|
|`city.coast`|杭州实际为空，旧岸线构建器按深圳南岸位置裁切并造对岸|从真实水体岸线与步道/挡墙证据独立生成岸边对象，不把空 coast 当成“杭州无岸线”|

`waterHeight` 可用钱塘江已有 0.9 game 作为**初始反射参考**。每个水体保持自己的估计水位，镜面仍随最近水体更新。它既不是全城水位，也不是潮位观测。沿用已有波纹导数滤波、反射 mipmap、固定刷新策略、材质灯光配置稳定性，无需新增每灯实时反射或每帧材质重编译。

## 当前输入统计

- 33,848 条道路中，2,406 条中心线与真实水面有 >0.1 game 的正长度交集：2,049 条源标桥、53 条源隧道、304 条未标桥。这是候选识别，不是物理通行验收。
- 明确桥段与湿区并集相交后为2,132条线片段。应保留很短的真实桥，不用旧脚本的8 game阈值隐藏它们。304条未标桥需要逐对象辨识涵洞/岸边误差/缺标签，不能一律抬高或一律删除。
- 既有街灯69,723条应原样作为独立 street lamps 输入。当前咖啡馆外圈内76条、城市阳台外圈内291条，内圈分别31、142条；现有局部光源有可选灯位，不需要复制街灯进400条上限的公园清单。
- 找到168个具名、面积≥1800 game²且距离水面≤40 game的绿地区域；这只是语义选址集，不是已放置灯具。钱江世纪公园B/C/D/E区及滨江公园可先挑真实步道边、干地且不挡入口的点。灯位属于estimated游戏布置，不能声称OSM实测灯杆。避免把12m泛光灯一律铺满西湖、寺院或历史园林。

详细逐路记录在 [crosswater-audit.json](crosswater-audit.json)，灯光和绿地记录在 [lighting-shore-audit.json](lighting-shore-audit.json)。全部仍需构建后的灯杆脚点、通行、夜景和性能验证。

## 岸距纹理契约与预算

只以v3真实湿区并集生成mask，保留岛屿孔洞。合并源水面和船闸语义分区的内部边，不把管理边界变成“岸”。裁切边界也不是真岸：需保留固定源未裁切水面延续，或剔除box边；不能在城市边界造泡沫。

使用无gamma的RGB8 PNG，R为 `round(min(distanceGame,120)/120*255)`，G为湿区mask。X/Z范围取city.meta.extent、每个像素中心与运行时UV一一对应。现有`invertY=false`要求生成行从zMin向zMax，必须以西湖、钱塘江和岛孔的非对称样本做解码及实机核对。只改图片名而方向翻转会导致错误浅水/岸缘。

本城市宽21,360.87、南北12,637.71游戏单位。4096×2424约5.21 game/texel，RGBA8含mip预算约50.5MiB；8192×4847约2.61 game/texel，约201.96MiB。R量化步长约0.471 game。PNG压缩文件小不等于GPU内存小。

建议先在隔离候选采用8192方案验证硬件纹理尺寸与内存，低画质4096需明确近岸损失；既有泡沫过渡仅1.5–6 game，不能把5.2 game像素宣称等效细节。若预算不成立，保留全城较粗场并增局部高分辨率clipmap属于下一项小运行时改动，需实测后取舍。距离计算用真实欧氏距离或记录像素误差的栅格距离；旧脚本8邻域侵蚀是近似，不应写成真实测量。

## 集成与验收顺序

1. 在隔离输出生成非空 crossings、非空具名公园灯位和实际岸距PNG；绑定city/source/road-levels/lamps哈希。`infrastructure.json`仍保持schema1字段，扩展source/heights/provenance而不改玩法接口。
2. 主集成调整crossing上限和校验，保留杭州source-node路高分支；补真实岸线模型/材质接收者、灯具与source道路/地标的所有权划分。
3. 检查每个桥片段的源序、对应高度、隧道排除、具名桥不重叠；每个灯的干地/入口/道路/树木间隙与模板高度一致；岸距非恒定且方向/距离/孔洞/crop边正确。
4. Blender与实机验证近岸和航拍、昼夜、西湖与钱塘江同时入镜、反射切换、桥下/引桥驾驶、灯脚与植被、冷启动与GPU内存/帧时。当前24组水体语义交叠及道路portal问题继续列未通过。
